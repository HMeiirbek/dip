# Отчёт: Модуль защиты конфиденциальности сетевого аудиотрафика

**Дата:** `Апрель 2026`  
**Статус:** `Готов к Production`

В данном отчёте приведена актуальная сводка о состоянии внедрения механизмов защиты, шифрования и маскировки пакетов согласно требованиям технической спецификации.

---

### 1. Защищённая аудиосвязь (WebRTC) и шифрование (TLS, DTLS, SRTP)
**Статус: Полностью внедрено**
* **Технология:** В основе медиа-трафика лежит стандарт `RTCPeerConnection`.
* **Шифрование:** Весь процесс обмена аудио пакетами (RTP) зашифрован с использованием надежных протоколов **DTLS-SRTP** (AES-GCM). Аудиопоток не попадает на сервер в открытом виде, сервер выступает исключительно в роли сигнального брокера и не способен перехватить звук между клиентами. Сертификаты и ключи сессии согласуются по стандарту через D/TLS handshake на стороне клиента.

### 2. Сигналинг только через защищённые соединения (HTTPS/WSS)
**Статус: Полностью внедрено и защищено**
* **Технология:** Обмен транспортными метаданными осуществляется через `socket.io` со строгой привязкой к транспорту `websocket`.
* **Инфраструктура:** На уровне `WsGateway` внедрён механизм инспекции соединения. Для Production сценариев (при установленном `ENFORCE_SECURE_SIGNALING='true'`) сервер отторгает любые инициализации, приходящие не из TLS/WSS доменов, что закрывает атаки типа "downgrade" и не позволяет сигнальному трафику течь в открытом виде (HTTP). Защита и терминация TLS поддерживается на уровне балансировщика, доставляя на Node.js безопасный контекст.

### 3. JWT-аутентификация для сигналинга + refresh flow
**Статус: Оптимизировано, Полностью внедрено**
* **Аутентификация сокета:** Каждое WebRTC-соединение инициируется только после проверки JWT (`socket.auth.token`). Любое подключение без валидного токена сбрасывается сервером на этапе handshake.
* **Seamless Refresh Flow:** Во фронтенд-приложении интегрирован автоматический Axios Response Interceptor и механизм очередей (Queue). При истечении токена `accessToken` система ловит ошибку HTTP `401 Unauthorized`, делает "паузу", незаметно для пользователя выполняет запрос `/auth/refresh`, и затем выталкивает отложенные запросы с новым Bearer токеном. Этот же новый токен динамически обновляется на стороне `socket.io` предотвращая обрыв звонков при долгой активности.

### 4. NAT traversal через STUN/TURN (включая TURN over TLS 443)
**Статус: Поддерживается, Готово для настройки среды**
* **Технология:** Метод `getIceServers()` автоматически считывает URLs из переменных окружения.
* **Маскировка (Masking):** Документирована политика `REACT_APP_ICE_TRANSPORT_POLICY=relay`. В случае строгих сетевых экранов (DPI), весь UDP медиа-трафик оборачивается в TCP/TLS пакеты, имитируя обычный веб-сёрфинг в адрес настроенного TURN-сервера (TCP:443). Прямые (host/srflx) кандидаты исключаются, обеспечивая максимальный уровень скрытности пакетов.

### 5. Мониторинг качества (RTT, jitter, packet loss, MOS-like)
**Статус: Полностью внедрено**
* Открыто регулярное 5-секундное измерение соединения. Метод `collectQualitySample` разбирает низкоуровневую статистику WebRTC (`pc.getStats()`), вычисляет `rttMs`, `jitterMs`, % `packetLossPct` и пропускную способность, чтобы сформировать единый индекс качества (суррогатный **MOS**).
* Полученные данные отправляются в базу по защищенному каналу для формирования дашбордов и истории аналитики звонков модераторами.

### 6. Модераторский/админский контроль
**Статус: Полностью внедрено**
* **Интерфейсы:** Интегрированы модули `<ModeratorPage>` и `<AdminPage>`.
* **Функционал:** Система обеспечивает полный обзор системы: от онлайн-пользователей (присутствие по сокетам — `moderation:presence-changed`) до активных звонков с мониторингом метрик качества.
* **Алерты и действия:** Реализован REST API для мгновенного прерывания звонка по инициативе администратора (`/admin/calls/:id/force-end`), а также система репортинга и установки флагов (warnings) на сессии.

### 7. Эксплуатационные параметры (SLA, Retry policy)
**Статус: Полностью внедрено**
* **Защита от DDoS (Rate Limiting):** Для поддержки 99.5% доступности и защиты от перебоев в модули API и Websocket внедрён глобальный Rate Limiter (библиотека `@nestjs/throttler`). В шлюзе работает спец-guard `WsThrottlerGuard`, который отбрасывает спам от скомпрометированных агентов.
* **Retry Policy:** В `socket.ts` настроена точная дисциплина повторных соединений: реконнект шагами `2s -> до 10s`, с учётом randomization (jitter-фактор 0.5) и лимитом в 5 попыток. Алгоритм не «душит» сервер одновременными запросами.
* Механизмы самого WebRTC способны удерживать качество звука при 5% потерях благодаря встроенным FEC (Forward Error Correction) и алгоритмам Jitter-буферизации браузеров.

### 8. Модуль визуализации сетевого аудиотрафика
**Статус: Полностью внедрено (по новому ТЗ)**
* **Функционал:** Разработан React-компонент `<TrafficVisualizer />`, встроенный во вкладку "Traffic". Модуль позволяет загружать дампы трафика (`.json` из Wireshark или классический `.pcap`) для анализа пакетов прямо в браузере (до 50-100 МБ) без отправки на сервер.
* **Аналитика:** Система автоматически вычисляет ключевые метрики потока (Средний размер пакета, Стандартное отклонение размера, Средний интервал, Jitter задержки).
* **Визуализация (Recharts):** Добавлены интерактивные графики:
  1. *Дисперсия размеров (Scatter)* — визуальное подтверждение "шумности" зашифрованного пакета.
  2. *Интервалы* — график задержек для доказательства неравномерности криптографического трафика.
  3. *Гистограмма распределения* — сравнение узкого диапазона (WebRTC) и широкого (Protected).
  4. *Плотность потока (Flow area)* — окна по 250мс для оценки общего объема.
* **Фильтрация и режимы:** Внедрены переключатели режимов (Normal / Protected) и фильтры по протоколам (UDP, TCP, TLS, RTP) для наглядных интерфейсных демонстраций в рамках дипломной работы.
